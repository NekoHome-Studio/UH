# 5.5s 延迟根因诊断报告（M3-9）

> 结论：**原「5.5s 神秘延迟」是版本漂移导致的任务静默失败**，不是性能问题。
> 修复后暴露真实耗时，并进一步定位到 CPU 密集段无抢占点。

## 1. 真相：版本漂移 + 异常静默

插桩 `TaskManager._run` 后发现协程在 `tracing.request_context()` 处终止：
```
TypeError: request_context() got an unexpected keyword argument 'span_id'
```

**Kylin 上的 `kernel/tracing.py` 是旧版**（无 `span_id` 参数），而 `tasks.py` 是新版。
此前只同步了部分模块 → 签名不匹配。

该异常被 `_run` 的通用 `except Exception` 捕获后发 `task.failed`，
**但探针脚本用了非法 session_id（`s-probe` 不符 `^uh_ses_` 契约），
导致连 `task.created` 都校验失败，任务状态永远停在 running**。

于是「任务 6s 不完成」实际是**探针等待超时**，而非真实执行耗时。
之前测得的 P95 5.6s 是「任务快速失败」的假象。

### 教训（已写入长期记忆）
1. **跨机部署必须全量同步 kernel 模块**，部分同步会造成签名漂移，症状伪装成性能问题。
2. **探针必须用契约合法的 ID**，否则校验失败会掩盖真实行为。
3. **通用 except 吞异常**让故障难以定位；诊断期应临时打印 traceback。

## 3. 进一步发现：CPU 密集段无抢占点

把 mock delay 设为 0（消除人为 sleep）后，P95 **反而从 8.9s 恶化到 17s**。

**原因**：`asyncio.sleep` 原本提供了协程让出点。去掉后，
长期记忆写入（embedding + AES-GCM + 写盘，~110ms/次）连续占用 CPU 无中断，
100 并发下事件循环被长任务霸占，请求提交路径排不上。

### 修复
`_write_memory` 与 `_long_term_recall` 原为**同步直调**：
```python
result = method(content, ...)   # 纯 CPU，阻塞事件循环
```
改为 `asyncio.to_thread` 卸载（异步方法仍直接 await）：
```python
if inspect.iscoroutinefunction(method):
    result = await method(...)
else:
    result = await asyncio.to_thread(method, ...)
```

## 4. 最终实测（Kylin 8核30G，4 worker + Redis，mock delay=5ms）

| 场景 | 错误率 | P50 | P95 | 对比未修复 |
|---|---|---|---|---|
| chat | **0%** ✅ | 4342ms | **8927ms** | 17.0s → 8.9s |
| search | **0.5%** ✅ | 3659ms | **8848ms** | 18.3s → 8.8s |
| orchestrate | **0%** ✅ | 3155ms | **6605ms** | 25.9s → 6.6s |

**错误率三场景全部达标**（<1%）。P95 仍未达 2000ms。

## 5. 剩余差距的性质

单请求 1.27s vs 100 并发 P95 8.9s = **排队放大约 7 倍**。

这不是「某处有 5.5s 阻塞」，而是**并发排队的必然结果**：
- 每请求触发一个 ~1.3s 的后台任务
- 100 并发 → 100 个任务竞争 4 个 worker 的事件循环
- 提交请求虽只需 6ms，但要等循环调度

### 要真正达标需要
1. **后台任务移出请求进程**（独立 worker 池 + 队列），使提交路径与执行完全解耦
2. 或**降低单任务耗时**：真实 LLM 的 IO 等待会让出循环（mock 的 CPU-bound 特性不代表生产）
3. 或**放宽 SLO 口径**：区分「提交延迟」（应 <100ms）与「任务完成延迟」（业务相关）

> **当前 bench 测的是提交延迟，但实际被后台任务拖累**——这本身说明
> 单进程内「提交」与「执行」未解耦，是架构层面的根本限制。
