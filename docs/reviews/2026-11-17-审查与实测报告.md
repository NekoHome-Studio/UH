## 0. 结论摘要

### 0.1 总体判断

UH! 的**契约层设计成熟度显著高于实现层与治理层**。M1 能力期的功能骨架已经搭起来，错误码、事件字典、响应包裹、隐私分级、MCP 抽象等设计考虑周全；但存在三类系统性问题：

1. **治理声称与事实源脱节**：README/PROGRESS 声称契约“已冻结、评审通过、111/111 全绿”，但契约正文仍写“冻结候选 / needs-review”，仓库内没有人工评审记录，也没有可复现的验证输出。
2. **门禁与 CI 名不副实**：默认环境跑 `pytest` 直接报无模块；`verify-all` 因硬编码 `python` 而 B2 失败；CI 只跑 Node 契约校验，不跑 pytest，也不跑 `verify-all`。
3. **实现存在可直接利用的安全与正确性缺陷**：WS 鉴权可绕过、确认令牌从无鉴权端点泄露、确认 TTL 只标记不过期唤醒、任意路径文件可被索引并检索外泄、WS 重订阅后实时事件永久丢失。

**当前状态不建议对外网暴露，也不建议把“M1 已验收”当成生产可用结论。**

### 0.2 实测一句话结论

| 项目 | 文档声称 | 本次实测 |
|---|---|---|
| Python 测试 | 111/111 | **110 passed / 1 failed**，且失败可稳定复现 |
| `verify-all` fast | 全绿 | 默认 PATH 下 **FAIL B2**；指定 Python 后 6/6 通过 |
| `verify-all --full` | 全绿 | 指定 Python 后 8/8 通过（含官方 OpenAPI/AsyncAPI 校验） |
| 高危安全项 | 未提及 | **5/5 运行时复现成功** |

### 0.3 修复优先级（只列建议，本次未修改任何代码）

1. **阻塞级**：WS 空 token 放行、REST 全局无鉴权、`/dev/confirmations` 令牌泄露、确认 TTL 死等、`index_document` 路径穿越。
2. **高危**：CI 不跑 Python 测试/门禁、门禁解释器环境依赖、CLI Windows 编码 bug、WS 重订阅丢实时事件。
3. **中危**：契约冻结状态回写与评审记录、文档状态漂移、无界内存增长、StorageGuard 未执行、CAP-3001 未进 REST 包裹、span_id 审计链自链自、依赖无锁、部署脚本非幂等。
4. **低危**：可变默认参数、异常消息透传、分页 `total` 语义、隐私分类器正则缺口、L2 加密失败静默吞。

### 2.1 pytest：110 passed / 1 failed

默认 `python` 直接失败：

```
C:\Users\haoxu\.workbuddy\binaries\python\versions\3.13.12\python.exe: No module named pytest
```

改用 `C:\Python314\python.exe`：

```
......F................................................................. [ 64%]
.......................................                                  [100%]
FAILED tests/unit/test_cli.py::test_up_down_integration - TypeError: argument of type 'NoneType' is not a container or iterable
1 failed, 110 passed, 77 warnings in 31.09s
```

单独重跑该用例仍然失败，排除偶发：

```
FAILED tests/unit/test_cli.py::test_up_down_integration
1 failed, 15 warnings in 4.50s
```

#### 失败根因

测试输出显示内核其实已经启动成功：

```
UH! 内核已起：http://127.0.0.1:59086 （pid 22440）
```

随后在断言 `cli._alive(pid)` 时崩溃：

```
kernel\cli.py:121: in _alive
    out = subprocess.run(["tasklist", "/FI", "PID eq %d" % pid], capture_output=True, text=True).stdout
kernel\cli.py:122: in _alive
    return str(pid) in out
E   TypeError: argument of type 'NoneType' is not a container or iterable
```

伴随的线程异常：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xcf in position 4: invalid continuation byte
```

**原因**：中文 Windows 的 `tasklist` 输出为 GBK/CP936，`subprocess.run(..., text=True)` 用默认 UTF-8 解码，读取线程抛异常，`stdout` 变成 `None`。这是确定性的平台兼容 bug，不是测试顺序问题。

**影响**：
- `PROGRESS.md:4,32,209` 声称的“111/111，本地+服务器”在本机不可复现。
- 该用例是 M0-6 “一键启动”验收项，失败意味着跨平台承诺在当前环境未成立。

**建议**：`kernel/cli.py:121` 改为 `subprocess.run(..., capture_output=True, text=True, encoding="utf-8", errors="replace")`，或直接避免依赖 `tasklist` 文本输出；并补一条中文 Windows 的 CI/测试矩阵。

## 3. 运行时复现（5/5 证实）

以下复现均在 commit `41442bc` 上实际执行，输出为实测结果。脚本见附录 A。

### R1 — WebSocket 鉴权可绕过

**条件**：设置 `UH_WS_AUTH_REQUIRED=1`，删除 `UH_WS_AUTH_TOKEN` / `UH_WS_TOKEN` / `UH_AUTH_TOKEN` / `UH_LOCAL_MODE`。

**步骤**：创建合法 session 与 task；用 `?token=attacker` 连接 `/api/v1/stream`。

**实测输出**：

```
=== R1 WS auth bypass (UH_WS_AUTH_REQUIRED=1, no token configured) ===
RESULT: WS ACCEPTED with arbitrary token 'attacker' (no 4401)
```

**代码位置**：`kernel/main.py:504-513`

```python
expected_token = os.environ.get("UH_WS_AUTH_TOKEN") or ...
auth_required = _truthy(...)
token = _bearer_token(params.get("token")) or ...
authenticated = not auth_required
if token and (expected_token is None or secrets.compare_digest(token, expected_token)):
    authenticated = True
elif token and auth_required:
    ...close(4401)
```

`expected_token is None` 时，任意非空 token 直接置 `authenticated=True`。首帧 `op:auth`（`:578-584`）中的 `expected_token is not None and ...` 判断同样失效。

**判定**：与 `docs/contracts/openapi.yaml:11-12` 的全局 `bearerAuth` 要求相反；生产若开启鉴权但漏配 token，鉴权完全失效。

### R2 — 确认令牌从无鉴权端点泄露

**步骤**：在 app 内创建一个高危确认请求，随后匿名 `GET /api/v1/dev/confirmations?task_id=...`。

**实测输出**：

```
HTTP status: 200
Token leaked in response: True
Leaked token prefix: uct-HVz0yHhx...
```

**代码位置**：
- `kernel/confirmation.py:60-74`：`ConfirmationRequest.to_dict()` 明确包含 `confirmation_token`。
- `kernel/main.py:460-466`：`/api/v1/dev/confirmations` 无任何鉴权，直接返回 `r.to_dict()` 与全部 audit。

**判定**：任何匿名调用者可取出待确认 token，再调用 `POST /api/v1/tasks/{id}/confirm` 自行批准高危工具，一次性防重放与任务绑定都失去意义。

### R3 — index_document 任意路径读取并经 search 外泄

**步骤**：在系统临时目录写入含唯一标记 `UH_REPRO_MARKER_7F3A9C` 的文件；通过 `RetrievalMCPServer.handle()` 调 `tools/call` → `index_document(path=<tempfile>)`；再用 `search` 查询该标记。

**实测输出**：

```
Index accepted: True
Marker retrievable via search: True
```

**代码位置**：
- `kernel/retrieval.py:189-201`：`_read_document(path)` 直接 `Path(path).read_text()` / `PdfReader(path)`，无目录白名单。
- `kernel/retrieval.py:218-220`：`index_document(path=...)` 调用 `_read_document`。
- `kernel/retrieval.py:250-252`：工具 `inputSchema` 只声明 `path: string`，无约束。
- `kernel/retrieval.py:278-279`：`tools/call` 将 `args.get("path")` 原样传入。

**判定**：可索引工作区外任意 `.md` / `.txt` / `.pdf`（如 `.env`、配置文件），并通过 `search` 检索出内容。配合 R2 中无鉴权的 `/dev/tool-task`（`kernel/main.py:454-458`，`tool_name` 与 `arguments` 完全由请求体控制），攻击链闭合。

### R4 — 确认令牌 TTL 到期后任务永久挂起

**步骤**：`ConfirmationManager(ttl_s=1)` + `TaskManager`，创建高危工具任务，FakeHost 在 `call_tool` 中调用 `confirm` 回调后等待；1.2 秒后尝试确认。

**实测输出**：

```
Status after 1.2s TTL: pending_confirmation
Expired resolve raised: UH-USR-1003 confirmation_token 已过期
Waiting future done after expiry: False
Status after expired resolve: pending_confirmation
```

**代码位置**：
- `kernel/confirmation.py:120-126`：过期分支只把 `req.status = "rejected"`、写审计、抛 `ConfirmationError`，**不触碰等待中的 future**。
- `kernel/tasks.py:126`：`decision = await fut` 没有任何定时器在 TTL 到期时 `set_result` / `set_exception`。
- 全仓库 `set_result` 仅 `kernel/tasks.py:154`（用户主动确认路径）与 `kernel/mcp.py:178`（MCP 响应路径），无 TTL 定时器。

**判定**：用户既不批准也不拒绝时，任务永远停在 `pending_confirmation`，`_confirm_futures`、订阅队列与事件缓冲均不释放。直接违反 `docs/contracts/events.md` 的“终态必居其一且必送达”。

**附带发现**：首次复现误用 `session_id="s"`，`_emit` 抛 `EventValidationError`，并以 `Task exception was never retrieved` 形式留在 asyncio 后台任务里。正常 REST 路径会生成 `uh_ses_...` 合法 ID，因此这是内部调用健壮性缺口，不是用户路径 bug。

### R5 — WS 重订阅后实时事件永久丢失

**步骤**：
1. 用慢 LLM（每 0.1s 一个 delta）创建任务，读到 `seq=3`。
2. 以 `?task_id=<tid>&after_event_id=0` 连接 WS，排空回放 `[1,2,3]`；此时 `queue_task` 正常建立。
3. 发送 `{"op":"subscribe","task_id":tid,"after_event_id":3}` 强制走重订阅分支（游标与初始不同，且等于当前 seq，故新 attach 无回放）。
4. 等待 2 秒看是否收到实时事件。

**实测输出**：

```
task status: running seq: 3
initial replay: [1, 2, 3]
seq right after re-subscribe: 4
RESULT: TIMEOUT after 2.0s - live events lost after re-subscribe
```

其中 `seq=4` 出现在重订阅过程中，说明那一帧仍属于 attach 的回放；此后没有任何实时帧送达。

**代码位置**：`kernel/main.py:604-608`

```python
if not (subscriber is not None and target == active_task_id and cursor == query_after):
    if queue_task is not None:
        queue_task.cancel()
        queue_task = None
    subscriber, done = await attach(target, cursor)
```

`attach()` 返回新的 subscriber，但 `queue_task` 没有被重建；主循环 `:612` 的 `if queue_task is not None and queue_task in done` 永远不成立。

**附加静态发现**：`kernel/main.py:488-492` 强制要求 query 参数 `task_id`，否则直接 4404。因此“不传 query task_id、靠首帧 `op:auth` 后再 `op:subscribe`”的路径在连接阶段就被拒绝；`op:auth` 分支（`:578-588`）在 `subscriber is None` 时调用 `attach()`，同样不重建 `queue_task`，属于同类 bug。UI（`ui/index.html:94-97`）恰好使用 query token 且不切任务，所以没暴露这个问题。

### 4.2 实现与运维

#### I1 — REST 全局无鉴权（静态确认）

`docs/contracts/openapi.yaml:11-12` 声明：

```yaml

  - bearerAuth: []
```

但 `kernel/main.py:221-250` 的 HTTP 中间件只做 trace 与幂等，无任何认证逻辑。无鉴权敏感端点包括：

| 端点 | 位置 | 风险 |
|---|---|---|
| `GET /memory/export` | `main.py:372-381` | `include_sensitive=False` 时无任何授权即可导出全部 L1 长期记忆明文 |
| `DELETE /memory/long-term` | `main.py:363-370` | 可清空长期记忆 |

| `POST /api/v1/dev/capability/{name}/toggle` | `main.py:468-471` | 可任意开关能力可用性 |

#### I2 — 多处无界内存增长（静态）

| 位置 | 问题 |
|---|---|

#### I3 — StorageGuard 声明但从不执行（静态）

`kernel/main.py:180-181` 注册能力时传入 `storage={"retrieval"}` / `{"orchestration"}`，`protocol.py:122-137` 定义了 `guard.declare()` 与 `check()`（后者抛 `UH-KRN-2010`）。但全仓库 grep **没有任何 `guard.check(...)` 调用点**，`CapabilityRegistry.call` 全程不校验存储声明。契约宣称的“存储隔离”没有强制点。

#### I4 — CAP-3001 降级未进 REST 包裹（静态）

`kernel/retrieval.py:24` 定义 `CAP_NO_RESULTS = "UH-CAP-3001"`；`kernel/tasks.py:210` 只在检索不可用时发 WS `task.degraded` 事件。`kernel/main.py:258-298` 的 `_envelope` / 响应归一化中间件从不写 `meta.degraded`，REST 层也没有 `error.code = CAP-3001`。与 `docs/contracts/errors.md:41` 描述的“HTTP 200 + data 正常 + meta.degraded=true + error 携带 CAP-3001”不符。

#### I5 — span_id “双向溯源”实为自链自（静态）

- `kernel/tasks.py:168`：`span_id=span_id or tracing.new_span_id()`，每次发射外部事件都新造随机 span。

### 4.4 值得肯定的设计

为避免报告只列问题，以下设计 Decisions 经审查认为是正确的：

1. **统一响应包裹兜底**：`kernel/main.py:258-298` 的中间件对所有 JSON 响应强制归一化 `{data,meta,error}` 并注入 `trace_id`，同时处理幂等回放，落地较完整。
2. **不可信内容边界**：`kernel/retrieval.py:39-57` 的 `sanitize_document` + `wrap_untrusted_content`，`tasks.py:223` / `orchestration.py:201` 注入 LLM 时显式标注“不可信数据”，具备 prompt-injection 防护意识。
3. **MCP 抽象与正确的超时取消**：`kernel/mcp.py` 提供 stdio / in-process / HTTP 三种 transport；`_request`（`:331-364`）用 `asyncio.shield` + `wait_for`，超时后 `transport.cancel()` + `task.cancel()` + await 回收，取消路径干净。
4. **隐私分级与加密**：L1 向量化 / L2 AES-GCM 密文 / L3 拒绝，L2 默认不进语义召回（`long_term_memory.py:267-272`）。
5. **一次性确认令牌结构**：`confirmation.py:115-119` 的一次性防重放、任务绑定、TTL 字段、`:134-146` 的 `tool.confirm` 审计结构清晰（唯 TTL 自动撤销缺失）。
6. **事件字典驱动**：`event_mapping.py:119-140,262-285` 用冻结 schema 做起出口校验与 `event_id` 连续性检查，未知事件直接拒绝。
7. **异步安全的链路追踪**：`kernel/tracing.py` 用 `contextvars`；`logging.py:54-61` 在发射时即绑定 trace / span，避免队列 handler 丢链路。
8. **依赖注入与零硬编码密钥**：LLM key、Master key、存储路径均走 env；大量构造参数可注入 mock（`LLMClient.client`、`MCPHost.transport`、`LongTermMemory.classifier`），测试友好性基础好。
