## 结论

**不通过**（就 v0.1.0 的发布质量声明而言）。

单进程核心功能可用，发布包签名链路可靠；但三处**声称与实际不符**：

1. 文档化安装路径下门禁是红的（418 passed / 3 failed，非 421 passed）；
2. `awrite/arecall` 使 to_thread 修复失效，100 并发 mock 实测 P95 **33.1s**、p50 **15.3s**，且「必须独立进程池」的根因结论不成立；
3. K8s 生产形态（replicas=2 且 Service 无 sessionAffinity + 任务状态进程内）开箱即出现跨 worker 404 / 幂等失效 / 长期记忆丢写。

另有 4 类「门禁能过但实质违规」的绕过样本。

## 发现（按严重度）

### P0 阻断

#### P0-1 文档化安装路径下 pytest 为红（418/3/16）

- 位置：发布声明 `RELEASE.md` / tag message；触发点 `deploy/security/`（无 `__init__.py`）
  + `kernel/enforcement` 侧的 `importlib.resources.files("deploy.security")`
- 复现：

```bash
git archive v0.1.0 | tar -x -C /tmp/uh010 && cd /tmp/uh010
python -m venv .venv && .venv/bin/pip install --no-compile -e .
.venv/bin/pip install pytest coverage httpx fakeredis pyyaml cryptography jsonschema
.venv/bin/python -m pytest -q -p no:warnings
# => 418 passed, 3 failed, 16 skipped
```

- 影响：发布门禁声明失真；CI 若按同一路径安装必然阻塞。
- 建议：给 `deploy/security/__init__.py`；或在 `pyproject.toml` 中把 `deploy*` 排除出包发现；
  并补一条「干净导出树 + editable 安装」的流水线回归。

#### P0-2 `awrite/arecall` 绕过 `to_thread()`，事件循环被长期记忆同步 I/O 阻塞；性能根因被误判

- 位置：[tasks.py](../../kernel/tasks.py#L641-L647)（`_write_memory`）、
  [tasks.py](../../kernel/tasks.py#L613-L622)（`_recall_memory`）、
  [long_term_memory.py](../../kernel/long_term_memory.py#L343-L347)（`awrite/arecall` 只是同步方法的协程壳）

```python
# kernel/tasks.py:641-647
# 注释：同步写入 ~110ms/次，直接在事件循环里跑会饿死提交路径
if inspect.iscoroutinefunction(method):
    result = await method(...)     # awrite 是协程函数 → 直接 await，to_thread 分支永不触发
else:
    result = await asyncio.to_thread(method, ...)
```

```python
# kernel/long_term_memory.py:343-347
async def awrite(self, *args, **kwargs):
    return self.write(*args, **kwargs)   # 同步体在事件循环内执行
async def arecall(self, *args, **kwargs):
    return self.recall(*args, **kwargs)
```

- 复现：`python -m kernel.serve`（1 worker）→
  `uh bench run --scenario chat --concurrency 100 --requests 200`，
  mock provider `delay=0`、空记忆库。实测 **p50 15347ms / P95 33104ms**；
  `asyncio` 调度探针测得单次 `awrite` 阻塞事件循环 **83.6ms**（方法本身 84.5ms），
  `arecall` 阻塞 **18.7ms**。5 并发 P95 **1477ms**（声称 186ms）。
- 影响：
  (a) 提交路径（建会话/发消息到 202）被后台任务的同步记忆 I/O 拖住，P95 劣化与并发线性相关；
  (b) `docs/reviews/2026-11-25-延迟根因诊断.md` 称「长期记忆已移出事件循环」，与代码实际相反；
  (c) 因此「需要独立执行进程池」这一 v0.2.0 方案建立在不成立的根因上——先修 `to_thread` 分支可能就能大幅收敛。
- 建议：把 `awrite/arecall` 改为 `await asyncio.to_thread(self.write, ...)` 的真异步实现，
  或让 `_write_memory/_recall_memory` 检测协程壳后仍走线程池；补「事件循环停顿 < 5ms」的回归测试。

#### P0-3 K8s 生产形态开箱不可用：replicas=2 + 无 sessionAffinity + 任务状态进程内

- 位置：`deploy/k8s/services.yaml`（`uh-kernel` 无 `sessionAffinity`）、
  `deploy/k8s/deployments.yaml`（`replicas: 2`）、
  [main.py](../../kernel/main.py) 中 `app.state.tasks` / `app.state.idempotency_cache` 为进程内、
  `_task_guard` 任务不在本进程时放行→后续 404
- 复现（双 app 实例模拟两 worker）：

```python
# 伪代码：同一 session，A 创建任务，B 读
A: POST /sessions/{sid}/messages -> task_id T (200)
B: GET /tasks/{T}        -> 404
B: GET /tasks/{T}/steps  -> 404
A/B: 同一 Idempotency-Key POST -> 生成两个不同 task_id（幂等失效）
```

- 影响：50% 概率的任务轮询/SSE/WS 404；幂等重放检测跨 worker 失效；
  `kernel/session_registry.py` 的 docstring 自己承认「需要粘性会话或独立任务路由」，但部署清单没有落实。
- 建议：短期在 `uh-kernel` Service 加 `sessionAffinity: ClientIP`（并注明这是权宜）；
  中期按登记项做 Redis 任务路由/状态外置。在此之前不应把该清单作为「生产可用」交付。

### P1

#### P1-1 `verify-compose-exposure.mjs`：`${VAR:?default}` 默认值可夹带明文凭据

- 位置：`scripts/verify-compose-exposure.mjs:12`（`ENV_REF` 接受 `:?default`）、
  同文件 `:35`（先剥离 `${...}` 再查内联凭据）
- 复现：`UH_AUTH_TOKEN: ${UH_AUTH_TOKEN:?hunter2-hardcoded-default}`、
  `DATABASE_URL: ${DB:?postgres://admin:pw@db}` → 门禁 0 errors；改成同值字面量则被拒。
- 影响：把明文凭据写进「合规」形态，绕过部署加固门禁。
- 建议：对 `:?` / `:-` 的默认值递归套用同样的凭据检测。

#### P1-2 `verify-security-hardening.mjs`：只看 `containers[0]`，initContainers 完全不受检

- 位置：`scripts/verify-security-hardening.mjs:81` `const container = pod?.containers?.[0];`
- 复现：在 `uh-kernel` 注入 `initContainers`，含 `privileged: true`、`runAsUser: 0`、
  `seccompProfile: Unconfined`、`capabilities: SYS_ADMIN`、`hostPath: /`，
  并给 Pod 加 `hostPID/hostIPC` → J 与 M 均 **0 errors**。
- 影响：M 项（seccomp/非 root）与 J 项（RBAC/权限）形同虚设，privileged initContainer 等价于节点 root。
- 建议：遍历 `spec.initContainers + spec.containers` 全部条目；
  显式禁止 `hostPID/hostIPC/hostNetwork`、禁 `hostPath` 挂 `/`。

#### P1-3 `secret-scan.mjs` 覆盖面过窄，且无 git 时 fail-open

- 位置：`scripts/secret-scan.mjs`（v0.1.0 仅
  `/\bUH_AUTH_TOKEN\s*[:=]\s*["']?([A-Za-z0-9_-]{20,})/g`）
- 复现：`OPENAI_API_KEY=sk-proj-...`、`AKIA...`、PEM 私钥、`UH_AUTH_TOKEN=abc123`（<20）
  全部 **0 命中**；在无 `.git` 的导出/发布树中脚本回退到空文件列表，
  打印 `SECRET_SCAN_PASSED (0 text files, 0 hits)` 并以 0 退出。
- 影响：v0.1.0 的「0 命中」是**扫描范围极窄**换来的，不等于无凭据；
  在制品包/CI 导出目录里扫描等于没扫。
- 建议：无文件时以非零退出；扫描本体加 AWS/OpenAI/GitHub/PEM/JWT 与长度 ≥8 的通用高熵键值；
  复用 `kernel/redaction.py` 的模式集。

#### P1-4 `verify-metrics-cardinality.mjs`：动态构造的指标注册可绕过 AST 检查

- 位置：`scripts/verify-metrics-cardinality.mjs`（基于静态 AST 匹配注册调用）
- 复现：`getattr(km, "Metric")("uh_review_high_cardinality", "...", ["user_id","session_id"])`
  → 门禁通过，且注册未被计数。
- 影响：高基数标签（user_id/session_id）可进 Prometheus，导致内存爆炸；
  门禁给出的「0 高基数」不可信。
- 建议：改为运行时采集（`REGISTRY` 快照校验 label 白名单），而不是静态匹配。

#### P1-5 `redaction.py`：短凭据 / 含空白 / 非 ASCII / 字面 `*REDACTED*` 前缀均可漏出

- 位置：[redaction.py](../../kernel/redaction.py#L52-L64)（`_looks_like_secret`：长度 24~512、禁空白、字符集受限）、
  [redaction.py](../../kernel/redaction.py#L71)（`if out is not text or REDACTED not in out:`）
- 复现（均实测漏出）：
  - 20 位 hex 密钥（<24）
  - `{"dbPassword": "..."}`、`{"authToken": "..."}` —— 键名不匹配 `_SENSITIVE_KEY` 的分隔符规则
  - `"abcdefg hijklmnop qrstuvwxyz 0123456789"`（含空格高熵）
  - 非 ASCII 高熵串
  - `"*REDACTED* sk-live-<高熵>"` —— 原文已含 `*REDACTED*`，**整段熵检测被跳过**

  对照组 `Bearer abcdefghijklmnop123456` 能正常脱敏。
- 影响：日志/记忆正文泄漏真实凭据；第 71 行的短路是本轮新发现的**逻辑漏洞**（并非长度阈值的老问题）。
- 建议：把第 71 行改为无条件执行熵检测；`_SENSITIVE_KEY` 支持 camelCase（`dbPassword`/`authToken`）；
  短凭据按「键名命中即整体脱敏」兜底，不依赖长度。

#### P1-6 L2 可被 `privacy_level` 显式降级为 L1 明文

- 位置：[long_term_memory.py](../../kernel/long_term_memory.py#L60-L62)（`classify` 中 `override` 直接返回）
- 说明：L3 已有「自动分级优先」保护（`write` 先跑 `auto` 再跑 override），但 **L2 没有**：
  内容被自动判为 L2（手机号/邮箱/敏感词），调用方传 `privacy_level="L1"` 即明文入 entries 并写入向量库。
  实测：L2 文本被写入明文 + 进入 `LocalVectorStore`。
- 影响：「L2 只存密文、语义索引不含 L2」的声明在**调用方显式降级**时不成立。
- 建议：与 L3 同构——`auto.level == L2` 时禁止降级到 L1，只允许升级。

#### P1-7 `_long_term_write` 静默吞掉所有异常（含 `MemoryKeyError`）

- 位置：[tasks.py](../../kernel/tasks.py#L629-L639) `except Exception: return`
- 影响：缺主密钥时 L2 写入被**静默丢弃**，无日志、无指标、无任务事件；
  与 RELEASE.md「fail-closed」的安全叙事表面一致，实际是「fail-silent」，用户数据丢失不可观测。
- 建议：至少 `log_event(WARNING, "memory.long_term.write_failed", ...)` 并计数器 +1；
  区分 `MemoryKeyError`（配置问题，应显式告警）与其他异常。

## 未能验证的部分

1. **4 worker + Redis 真实多进程**：用户指定的复现需要 Linux + `ss`；本机 Windows 下
   `kernel.serve` 的 fork/spawn 语义不同。已用双 app 实例 + 共享会话注册表模拟，
   结论方向成立，但**未在真 Linux 多进程下取数**。
2. **真实 LLM provider**：无密钥，全部基于 mock（CPU-bound `sleep`）。
   P0-2 的结论在 mock 下已经成立（延迟纯来自事件循环阻塞），但换成真实 LLM 后记忆 I/O 占比会下降，
   **P95 绝对值会变**——不过「根因不是进程池」的定性不受影响。
3. **macOS SBX 矩阵**：无主机，RELEASE.md 已登记。
4. **GitHub Release 8 个附件的真实性**：只读约束下未下载核对；只验证了本地构建产物。
5. **Compose / K8s 真环境实跑**：只做了清单的静态绕过验证，未部署到集群。
