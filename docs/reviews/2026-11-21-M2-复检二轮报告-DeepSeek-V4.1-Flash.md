## 5. 新发现

> 严重性口径：P0 阻断结项 / P1 应在结项前修或明确登记为 M3 硬性项 / P2 登记改进。

### F1（P1）R-2 凭据剥离清单不完整，5 个内核凭据 env 仍进 tool 子进程

- **位置**：`kernel/sandbox.py:410-413`（denylist）vs `kernel/main.py:163,166`、`kernel/long_term_memory.py:165`、`kernel/main.py:652`、`kernel/orchestration.py:183`
- **现象**：`build_plan` 只 pop 7 个键，但内核实际读取的凭据类 env 共 12 个，以下 5 个**未剥离**：

  | env | 内核用途 | 被插件窃取的后果 |
  |---|---|---|
  | `UH_CLIENT_ID_SECRET` / `UH_CLIENT_ID_SECRET_FILE` | 签名 `client_id`，绑定会话归属（main.py:155-175） | **伪造 client_id，冒充他人会话/task owner** |
  | `UH_MEMORY_MASTER_KEY` | 长期记忆加密主密钥（long_term_memory.py:165） | **解密长期记忆库** |
  | `UH_MEMORY_EXPORT_TOKEN` | 记忆导出（含敏感项）授权令牌（main.py:652） | **导出全部含敏感内容的长期记忆** |
  | `UH_CHECKPOINT_POSTGRES_URL` | 编排检查点 DB DSN（orchestration.py:183） | 凭据外泄（当前后端未实装，影响待定） |

- **实测**：探针 `.work/probe/probe1.py::env_strip` 注入 sentinel 后 `other_uh_keys_left` 含 `UH_MEMORY_MASTER_KEY` 等；`stripped_absent` 恰为声称的 7 键。
- **根因**：`env = os.environ.copy()` + 名字 denylist。**内核每新增一个凭据变量就静默泄漏**（denylist 与代码演进天然不同步）。
- **建议**：tool 子进程改**白名单 passthrough**（显式列出 SYSTEMROOT/PATH/PYTHONPATH/UH_SANDBOX_* 等），而非 copy-all-then-pop。属实现层修正，不动契约。
- **定位**：R-2 的**字面验收条件成立**（7 键确已剥离），但**其安全目标未达成**。

### F2（P1）`fs.host.read` 权限可经受制裁 SDK API 读取内核 bearer token

- **位置**：`kernel/sandbox.py:100-101`（`check_path` 对 `fs.host.read` 直接放行任意路径，**无敏感路径 denylist**）；`docs/contracts/manifest/common.schema.json` `$defs.permissions` 枚举合法包含 `fs.host.read`
- **实测**：`.work/probe/probe1.py::host_read_token` → `allowed: true`，成功读出 `.work/server-auth-token.txt` 全文（43 字符；报告不回显内容）。
- **影响**：R-2 要防的"签名但越权的插件夺 bearer token"，经此通道**依然可达**：插件声明 `fs.host.read` → `context.read_text("<token 路径>")` → 拿到内核 token → 以内核身份调 API。而 SDK 文档的权限表（`docs/sdk/python-tool.md:101-106`）**没有列出 `fs.host.read`**，第三方不会预期它存在，运维也不会预期它这么强。
- **建议**：①`check_path` 增敏感路径 denylist（`.auth-token`、`*token*`、信任库、`.uh/*.json`）；②对 `fs.host.read` 加装机信任门槛/操作员知情确认（契约只增不改 → M3 编号）；③SDK 文档权限表补该行为并标注高危。

### F3（P1）SDK 文档 `dev --once` 与实现相反 —— R-3 仍有假陈述

- **位置**：`docs/sdk/python-tool.md:88`（"`uh plugin dev ./my-tool --once` 灌入 initialize→tools/list→tools/call，期望 JSON-RPC 结果"）与 `:91`（"`dev --once` 完成实际 MCP 握手与工具枚举"）vs `kernel/cli.py:365-368`（`start(); if args.once: return process.wait()` —— **只启动进程并等退出，不注入任何 JSON-RPC**）
- **实测**：`plugin dev … --once < /dev/null` → **无任何输出，rc=0**（静默假成功）；对照手工喂 3 行 JSON-RPC → `initialize`/`tools/list`/`tools/call` 三条正确响应。
- **影响**：第三方按文档验收自己的插件会得到"空白 + 退出码 0"，既无法判断插件是否可用，也无法区分"文档错"与"我写错了"。这是本轮 R-3 专项里**唯一与实现矛盾**的指令，且正好落在 R-3 声称修复的那一节。

### F4（P2）静态扫描 6 类新绕过（R-1 加固未覆盖）

- **位置**：`kernel/plugins.py:408-441`（`resolve()` 只解析 `Name`/`Attribute(Name)`；`aliases` 归一化有错位）
- **实测矩阵**（`.work/probe/probe1.py`，18 样本）：

  | 样本 | 结果 |

  | `os.__dict__['system']('id')` | **PASS** |

  | `g = getattr; g(os,'sys'+'tem')('id')` | **PASS** ← getattr 变量化后不再是 `Name('getattr')` |
  | `(lambda:0).__globals__['__builtins__']['__import__']('os').system('id')` | **PASS** |

- **定位**：静态扫描是**审查辅助**，不能作为安全边界。建议在 M2 结项说明中明确该定性，并把"绕过面收敛"排到 M3（或改为 AST 污点分析/禁用动态调用）。

### F5（P2）非 UTF-8 源码被静态扫描静默跳过

- **位置**：`kernel/plugins.py:404-407`（`ast.parse(content.decode("utf-8"))` 失败即 `continue`）
- **实测**：`main.py` 首行 `# -*- coding: latin-1 -*-` 且含 `\xe9` → `UnicodeDecodeError` → **跳过扫描，validate 放行**；而 Python 装载该文件时会按 coding cookie 正常解码执行。
- **影响**：混淆载荷（非 UTF-8 源）完全绕过静态扫描。

### F6（P2）原生二进制 / 任意扩展名入口无静态扫描覆盖

- **位置**：契约 `common.schema.json` `$defs.entry` pattern 允许任意扩展名；`kernel/sandbox.py:136` 对非 `.py/.js` 入口直接 `return [str(entry)]` 执行；`kernel/plugins.py:393,402` 静态扫描只覆盖 `.js/.mjs/.cjs/.ts/.py`
- **实测**：manifest `entry: payload.exe` + 伪造 PE 头 → `validate` **放行**，`static_scan: []`，`files` 含 `payload.exe`。
- **影响**：SBX-02"拒绝危险 exec"可被"直接交付原生可执行文件"完全规避。

### F7（P2）出网导入告警漏检 2 类

- **位置**：`kernel/plugins.py:415-420`（`from X import Y` 只比对 `node.module` 本身）
- **实测**：`from urllib import request` → 无 `network` 告警；`from socket import socket` → 有告警（因 `mod="socket"` 命中）。前者导致 `allow_hosts` 声明要求被静默跳过。
- **影响**：仅告警级（真正拦截依赖运行时既有策略），但使 `allow_hosts` 声明缺失不被发现。

### F8（P2）非主题包无解压体积上限（zip bomb → 内核 OOM）

- **位置**：`kernel/plugins.py:785`（`{name: archive.read(info) for …}` 一次性全量解压到内存）；体积限制仅 `_validate_theme_sizes`（theme 专属，`themes.py:82` 8MiB）
- **复现**：构造 tool 类型 `.uhpkg`，单条目声明压缩前 4GiB 的零字节流 → `install`/`validate` 阶段内核进程内存暴涨。
- **建议**：解压前用 `ZipInfo.file_size` 预检总/单项上限，超限即拒。

### F9（P2）`tools/call` 对 dict 返回值返回 Python repr 而非 JSON

- **位置**：`kernel/plugin_sdk.py:117-119`（非 MCP content 列表的返回值走 `str(value)`）
- **实测**：文档 §3 的 `hello` 例子返回 `{"greeting": ...}`，实际 `tools/call` 文本为 **`{'greeting': 'hello chain'}`**（单引号 Python repr）。
- **影响**：第三方 MCP 客户端若按 JSON 解析 content 文本会失败；文档示例恰好踩中。

### F10（P2）SBX-04 实机形态与契约措辞不符 + Job 级总量缺失

- **位置**：`kernel/sandbox.py:531-535`（`LimitFlags = PROCESS_MEMORY | KILL_ON_JOB_CLOSE`，`JobMemoryLimit` 保持 0；`JOB_TIME` 用 CPU 时间非墙钟）
- **实测**：64MiB 限额 → 57MiB 处 `MemoryError`、rc=0、未 kill；契约 `configBase.memory_limit_mb` 描述为"超出 OOM Kill"。
- **影响**：①行为差异（插件可捕获 `MemoryError` 继续跑）；②仅 per-process 限制，多进程（Job 内多个子进程）可叠加突破总量。

### F11（P2）服务器存在两个 kernel 进程，监听 PID 归属异常；launcher 清理过滤器有盲区

- **现象**：`Get-NetTCPConnection -LocalPort 8080 -State Listen` 与 `netstat -ano` 均指向 **PID 12144**，其 `ExecutablePath=D:\Python312\python.exe`、命令行 `-m uvicorn kernel.main:app --host 0.0.0.0 --port 8080 --no-access-log --log-level warning`；另一 **PID 10608 = `D:\uh\.venv\Scripts\python.exe`**，同秒创建（`2026/11/21 12:26:09`），但**不持有任何监听 socket**。
- **矛盾点**：`D:\Python312\python.exe` 实测 `import fastapi / uvicorn / yaml` 全部 `ModuleNotFoundError`，理论上无法启动该内核；而服务对 `/health`、`/api/v1/plugins`、`/api/v1/themes` 均正常响应且鉴权生效。
- **风险（机制层，与本次结论无关但影响后续轮次）**：磁盘哈希一致性 ≠ 服务进程实际加载的代码。若某次部署后残留旧监听进程，哈希仍会全 SAME 而服务跑旧码。本轮侥幸成立（进程 12:26:09 晚于文件 12:24），**属偶然而非机制保证**。
- **附带缺陷**：服务器上的 `D:\uh\deploy-uh.ps1` 用 `Get-Process python | Where Path -like 'D:\uh\*' | Stop-Process` 清理 → **杀不掉 `D:\Python312` 实例**；仓库 `scripts/server-deploy.ps1` 与服务器 `start-uh.ps1` 按命令行 `*uvicorn*kernel.main*` 清理则没有此问题。
- **建议**：运维侧清理重复实例并统一到 `start-uh.ps1`；把停机逻辑改为**按端口归属 PID**（`Get-NetTCPConnection -LocalPort 8080`）而非路径/命令行匹配；复检报告增加"监听进程 PID + 创建时间 + 磁盘 mtime"三元组作为标准证据。

### F12（P2，证据缺口）服务器 M2 持久态为空，跨机安装/重激活无可复核证据
