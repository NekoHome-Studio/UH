# M3 生产期独立复审

审查日期为 2026-11-27。以 `m2-v0.1.0` → `v0.1.0` 为 M3 交付范围，同时在 `main@6ee7b83` 核对发布后的修复。生产放行仍有阻断项。GitHub 结项和发布记录继续反映历史交付状态。

## 审查发现

### P1 · 会话读取与关闭缺少完整的归属校验

`GET` 和 `DELETE /api/v1/sessions/{id}` 在本地元数据未命中时接受共享注册表的存在性结果，但随后 `_session_guard` 只读当前进程的属主映射。无本地属主或请求缺签名身份时，守卫允许继续。生产模式的全局 Bearer token 校验通过后，读取和清除 L0 仍缺少同一会话的归属验证。这两个入口是在 release tag 后为补足 OpenAPI 路由而加入的。由共享注册表读取属主，并统一采用严格模式下消息入口的身份要求。[`kernel/main.py` 会话守卫](../../kernel/main.py#L817) · [`kernel/session_registry.py`](../../kernel/session_registry.py)

### P1 · 会话关闭状态不跨副本传播，仍可提交消息

关闭操作只改处理该请求的进程内元数据，发消息仍只检查会话存在。两份本机 ASGI 应用共用一个会话注册表，使用同一合法属主验证。A 建会话，B 关闭返回 `closed`，A 查询仍返回 `active`，关闭后 A 发消息收到 `202`。B 查询还会用查询时间填充缺失的 `created_at`。共享会话状态应包含属主、创建时间和关闭状态，读、写及关闭使用同一状态，并核验在途任务是否会在关闭后回写 L0。[`kernel/main.py` 会话关闭与消息入口](../../kernel/main.py#L849)

### P1 · Compose、K8s 的检索与编排 Deployment 没有承接内核请求

两套清单给检索和编排声明了独立服务。默认内核只连接共享存储，检索的 MCP host 使用 `InProcessTransport`，编排直接实例化内核进程内的 `OrchestrationService`。即使外部能力镜像可用，提高这两个 Deployment 的副本数也分摊不了该路径的负载。对这些 Deployment 做 OOM 演练也无法证明承接真实流量的能力已隔离。需要接通两个远程调用路径，再验证 HPA 和故障降级。[`kernel/main.py` 能力初始化](../../kernel/main.py#L298) · [K8s 工作负载](../../deploy/k8s/deployments.yaml#L100) · [Compose 工作负载](../../docker-compose.yaml#L49)

### P1 · 非结构化消息和异常栈绕过日志脱敏

`JsonFormatter` 仅把 `record.fields` 交给脱敏器。普通日志文本会原样进 `event`，格式化异常原样进 `exc_info`。用本机合成记录验证，同一标记在结构化 `password` 字段已被替换，在 `event` 和 `exc_info` 仍可读取。内核的未处理异常分支会调用 `log.exception`。另外，压测客户端把 Bearer token 放在查询字符串，默认 Docker 启动保留 Uvicorn access log，本机安装版 Uvicorn 的 access log 路径含查询串。补齐日志落地前的文本脱敏并保留 trace/span，压测客户端改用 `Authorization` 请求头。[`kernel/logging.py` 序列化](../../kernel/logging.py#L31) · [`kernel/main.py` 异常处理](../../kernel/main.py#L524) · [压测请求](../../kernel/bench.py#L127) · [默认镜像启动命令](../../Dockerfile#L38)

### P1 · K8s 默认追踪链路在发送端和 Collector 配置两处断开

K8s 清单开启了 `UH_OTEL_ENABLED`，默认 Docker 构建只安装 `compose` extra，所需 SDK 和 OTLP exporter 位于 `otel` extra。内核遇到导入失败会降级到无追踪模式。Collector 使用浮动镜像标签并配置已于 v0.111.0 移除的 `logging` exporter，按当前镜像配置推断会在加载 pipeline 时失败。需要使用含 OTel 依赖的部署镜像、固定 Collector 版本并校验配置，再核对一条实际 span 能到达接收端。[内核 Dockerfile](../../Dockerfile#L6) · [Collector 配置](../../deploy/k8s/observability-k8s.yaml#L62) · [OpenTelemetry 移除公告](https://github.com/open-telemetry/opentelemetry-collector/issues/11337)

### P1 · 发行包有 SBOM，内核镜像标注的 SBOM 文件缺失

默认 Dockerfile 复制生成脚本并在 OCI 标签声明 `/app/dist/sbom.cdx.json`，没有运行生成器或复制产物，按现有指令构建的镜像不含该路径。N 项检查在仓库侧生成清单，无法证明 M3-8 的镜像验收条件。把构建产物放到声明路径并从最终镜像验收可读性和内容。[Dockerfile 构建步骤](../../Dockerfile#L19) · [供应链门禁](../../scripts/verify-all.mjs#L178)

### P2 · 只改 K8s、安全配置或 Desktop 时不会触发对应门禁

`push` 和 `pull_request` 的 `paths` 未包括 `deploy/k8s/**`、`deploy/security/**`、`desktop/**`，也漏了相应的 J、L、M 校验脚本。单独修改相关文件不会触发 `contracts.yml`，即便本地全量门禁能发现问题。让触发范围覆盖各项校验的配置和脚本。[CI 工作流](../../.github/workflows/contracts.yml#L2) · [GitHub Actions 路径过滤规则](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore)

### P2 · Windows 的 Git 测试夹具污染后续密钥门禁的子进程环境

当启动环境含空值的 `GIT_CONFIG_VALUE_0`，Git HTTPS 安装夹具覆盖再恢复此配置后，后续子进程保留 `GIT_CONFIG_COUNT` 却缺少配对值。全量 pytest 在密钥扫描用例报 `missing config value GIT_CONFIG_VALUE_0`。只运行这组 Git 测试和扫描测试复现 1 通过、1 失败。启动前仅对测试子进程移除继承的 Git 配置键，两例均通过。独立运行扫描通过且 0 命中。可将夹具的 Git 配置全部限定在其子进程环境，保留扫描失败时的非零返回。[Git 夹具](../../tests/unit/test_plugins.py#L724) · [仓库扫描测试](../../tests/unit/test_secret_scan_coverage.py#L59)
