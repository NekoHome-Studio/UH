## 生产链路八项验收

### 1. 鉴权与业务端点：通过

在 `UH_LOCAL_MODE=0 + UH_AUTH_REQUIRED=1 + UH_AUTH_TOKEN` 下，遗留 `/memory/*`、`/plugins` 别名和 `/api/v1/*` 业务端点无凭据返回 401，ops 端点保持 200；单设 `UH_AUTH_REQUIRED=1` 也会启用鉴权，401 包含 `meta.trace_id`。

### 2. WS 实时流：有条件通过

首帧 auth、实时 delta、after_event_id 回放和归属校验的回归测试通过。外部任务句柄仍有 URL 形状问题，见 P1-1。

### 3. 工具确认：有条件通过

inline approve/reject/timeout、RPC 高危工具 fail-closed、风险级不可降级均通过回归测试；fail-closed 事件序列和审计溯源仍不完整，见 P1-3。

### 4. 取消与终态：有条件通过

取消会补闭合 step、撤销 pending token，并在终态重复 cancel/resume 时返回 409。resume 后重新启动的 runner 没有登记回任务对象，随后 cancel 不能真正取消恢复执行，见 P1-4。

### 5. 超窗回退：不通过

运行中任务的热事件缓冲会裁剪旧 `step.started`，`/steps` 从热缓冲重建，超窗后不能保证全量阶段；运行中步骤还返回 `duration_ms: null`，与 OpenAPI 的整数类型不符，见 P1-5。

### 6. 隔离与隐私：有条件通过

REST 鉴权别名、L3 override、LocalVectorStore guard、L2 不入语义索引等回归通过。Chroma/LlamaIndex 后端的 add/query 没有调用 guard，生产切换后可绕过存储命名空间隔离，见 P1-2。

### 7. 幂等与响应契约：有条件通过

body、调用者和 in-flight 锁已纳入缓存键，Set-Cookie 不会从回放响应泄漏；但锁表没有 TTL/容量回收，持续使用唯一幂等键会单调增长，见 P2-1。

### 8. UI 与回退体验：有条件通过

状态机、游标重连、4408 steps 渲染、degraded 徽标和 4401 错误路径已有代码/回归覆盖。确认请求失败后按钮保持 disabled；本轮未把浏览器 UI 当作完整生产 E2E 通过，见 P2-2。

## 新发现

### P1-1：`stream_url` 仍可能不是可直接连接的 WebSocket URL

[kernel/main.py:480](../../kernel/main.py:480) 到 [kernel/main.py:486](../../kernel/main.py:486) 在未配置 `UH_PUBLIC_BASE_URL` 时返回相对路径 `/api/v1/stream?...`；配置 `UH_PUBLIC_BASE_URL=https://uh.example` 时则原样返回 `https://...`，不会转换为 `wss://`。契约示例要求客户端可直接用 `wss://<host>/api/v1/stream` 建立连接。实测分别得到相对 URL 和 `https://uh.example/...`；当前 UI 自己拼 URL，掩盖了外部 SDK 的问题。

### P1-2：Chroma/LlamaIndex 后端绕过 StorageGuard

[kernel/retrieval.py:155](../../kernel/retrieval.py:155) 到 [kernel/retrieval.py:176](../../kernel/retrieval.py:176) 的 `ChromaVectorStore.add/query` 没有调用 `_guard_access`，构造函数也没有接收 guard；`LlamaIndexChromaStore` 继承同一路径。`RetrievalService` 在 `chroma` / `llamaindex` 后端下创建的存储没有命名空间运行时校验，违背 M1-1 存储隔离契约。

### P1-3：高危 fail-closed 路径缺少 `tool.result`

[kernel/mcp.py:530](../../kernel/mcp.py:545) 在高危工具没有 confirm 回调时直接抛出 `UH-USR-1002`。此前已经发布了 `mcp.tool.call`，但该分支没有发布 `mcp.tool.result(status=denied)`。实测事件序列只有 `mcp.tool.call`，没有对应结果事件；任务流因此无法满足 `tool.call → tool.result` 配对约束。

同一链路的 [kernel/tasks.py:55](../../kernel/tasks.py:55) 到 [kernel/tasks.py:64](../../kernel/tasks.py:64) 没有把内部 `env.span_id` 传给 `_emit`；MCP 总线发布也未设置 span。确认审计 [kernel/confirmation.py:154](../../kernel/confirmation.py:154) 到 [kernel/confirmation.py:166](../../kernel/confirmation.py:166) 仍只写内存列表和日志，未形成带内部 span/event_id 的审计事件。

### P1-4：resume 后 cancel 不会取消新的 runner

[kernel/tasks.py:381](../../kernel/tasks.py:381) 到 [kernel/tasks.py:384](../../kernel/tasks.py:384) 启动 `_resume_workflow`，但没有把新 task 写回 `task["_runner"]`。`cancel()` 只取消旧 runner；实测恢复任务后，`task["_runner"]` 仍指向已完成的旧任务，调用 cancel 后恢复 coroutine 仍继续运行。

### P1-5：超窗 `/steps` 不完整，运行中步骤字段也不符合 schema

[kernel/tasks.py:249](../../kernel/tasks.py:249) 裁剪运行中任务的 `event_buffer`，而 [kernel/tasks.py:182](../../kernel/tasks.py:203) 完全从该缓冲重建 steps。将任务保持运行并模拟旧事件出窗后，`steps()` 返回空列表，丢失已经发生的步骤。运行中 step 还返回 `duration_ms: null`，而 OpenAPI `Step.duration_ms` 定义为 integer（可选但不可为 null）。

### P1-6：不存在的 session 仍可创建任务

[kernel/main.py:465](../../kernel/main.py:486) 没有 session 注册表或存在性校验。`POST /api/v1/sessions/uh_ses_missing/messages` 实测返回 202 并创建任务，契约要求不存在会话返回 `UH-USR-1003`。

### P2-1：幂等锁表没有回收

[kernel/main.py:130](../../kernel/main.py:131) 创建 `idempotency_locks`， [kernel/main.py:264](../../kernel/main.py:264) 为每个新键永久插入锁；后续 TTL/容量回收只处理 `idempotency_cache`，不处理锁表。实测 7 个唯一键后 `len(app.state.idempotency_locks)==7`，持续唯一键会造成进程内内存增长。

### P2-2：UI 确认请求失败后按钮无法恢复

[ui/index.html:112](../../ui/index.html:112) 到 [ui/index.html:119](../../ui/index.html:119) 在发起确认请求前立即禁用批准/拒绝按钮；HTTP 失败或网络异常只展示错误，不重新启用按钮，用户无法再次提交有效确认。

### P2-3：CLI reset 存在进程退出竞态

[kernel/cli.py:133](../../kernel/cli.py:141) 的 `dev_down` 发出 taskkill 后立即返回，[kernel/cli.py:165](../../kernel/cli.py:169) 随即删除日志，没有等待子进程完全退出或对删除做重试。完整 pytest 首次运行中 `test_reset_cleans_logs` 失败，单测隔离重跑通过，表现符合该竞态。
