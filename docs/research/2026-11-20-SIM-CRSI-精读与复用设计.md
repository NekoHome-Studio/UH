| 代际链 CRSI > 每代重新 RSI | Gemini 2.5→3.5→3.8→4：+3.5 / +1.6 / −0.8（Table 1） | 单链描述性 |

## 1. SIM 完整机制（可直接复刻的部分）

### 1.1 数据结构（App D.3，原文 schema）

每次运行一个 JSON 文件：

```json
{
  "next_id": 10,
  "carried_from": { "arm": "<source run>", "domain": "coding_enriched", "into": "<target run>" },
  "aliases": { "P6": "P5" },
  "problems": [
    {
      "id": "P5",
      "name": "premature completion without execution verification",
      "opened_round": 6,
      "attempts": [
        {
          "round": 6, "sample": "s2", "accepted": true, "backfilled": false,
          "domain": "coding_enriched",
          "what": "Implemented ExecutionGatingInterlock ... (修改+理由，存储时截断)",
          "files": "execution_gating_interlock.py, terminus_2.py",
          "predicted": ["circuit-fibsqrt", "configure-git-webserver"],
          "fixed": ["circuit-fibsqrt", "configure-git-webserver"],
          "missed": [],
          "passed": 49, "total": 60
        }
      ]
    }
  ]
}
```

字段语义要点：

- `name` = **根因假设**（不是症状、不是修改名）；`opened_round` 记录首次诊断轮次，读 ID 时必须结合其运行上下文。
- `predicted` 在**评估之前**写入（预计修好哪些任务），评估后回填 `fixed` / `missed`。同一任务在不同轮的预测是独立观察。
- `accepted` = selector 当轮选中，**即使 predicted 全落空也照样入账**（P8 案例：2 次尝试均被选中，0/4 预测兑现，记录保留）。
- `passed/total` = 该尝试在 evolve 集上的成功/总试次。
- `domain` = 来源上下文（benchmark/policy/round 的 provenance），跨运行继承时靠它区分源/目标尝试。
- `aliases` 保留被合并条目的旧 ID（P6→P5），历史不丢。
- `backfilled` 字段存在于存储 schema（D.3 仅列出字段名，未解释语义；按名字推断为"事后补录"标记——**此为推断，非论文原文**）。

### 1.2 更新规则（§3.2 + App D.1）

1. 每个提案**必须引用一个已有根因 ID，或命名一个新根因**；引用关系在评估前写进当轮 change manifest（先锁定，防事后合理化）。
2. 每轮**只记录被选中的候选**（含失败/回退的修改）；未选中提案不入账。无候选被接受则记忆不变。
3. 条目匹配由 **proposer 自己判断**（无独立相似度模型）；根因文本完全相同的条目**确定性合并**，保留全部 attempts。
4. 修改后来被改掉/替换，**其记录仍留在 SIM**（P8 的 round-4 阻塞路径后来被移除，记录保留）——最终 harness  alone 会丢掉这段搜索史。

### 1.3 注入方式与 8 条 prompt 规则（App D.2）

proposer 的 system prompt 与 selector 的评审上下文都**全文注入 SIM，不做检索、不截断**（其规模约 10 个条目量级）。规则原文译述：

1. 条目是先前经验，允许选择不同的修改（不是指令）。
2. 核对每条条目背后的 domain / benchmark / model。
3. 当前失败能被已有诊断解释时，从该诊断出发。
4. **复用理由（rationale），但在 benchmark 或模型变更后重新评估具体修改**。
5. 新证据充分时，修订、替换或推翻已有修改。
6. 只有新证据正当时才重访已试过的方向（防重复试错）。
7. 已有诊断解释不了当前失败时，新开问题条目。
8. **任务级证据的权重随场景距离衰减**：场景相似权重高，benchmark 和 model 都变了权重低。

### 1.4 四个作用（App F.6，案例支撑）

1. **理由决定保留**：engineering 里仅 harness 续优化第一轮就把继承的 prompt 指南回退成种子；Full SIM 全程保留并扩展（§F.5.4）。
2. **理由可迁移，实现需修订**：完成门"需要执行证据"的需求跨 benchmark 成立，但"什么算充分证据"变了（可行 ≠ 最优）。
3. **新结果给旧诊断追加证据**：P3 一个诊断下挂源轮 1/4 兑现 + 目标轮 0/2、1/2 兑现，未兑现预测对后续轮可见。
4. **修改被替换后经验仍在**：P8 保留被改掉的阻塞尝试及其未兑现预测。

## 2. 迁移规律（App F.5, Table 8 —— 对 UH! 多模型可插拔最有价值）

跨 4 领域 × 2 种迁移（换数据集 / 换模型）的机制复用分类：

| 迁移类型 | 直接复用 | 需适配 | 继承并扩展 | 场景依赖（需重估/可能闲置） |
|---|---|---|---|---|
| 换数据集 | 执行/传输/进程层、索引与检索器、工具调用拦截点、软门插入位置 | 传输细节（按键归一化、前台检测）、检索常数（top-k/阈值/配额）、证据探针（文件系统→调用历史） | 完成契约（加目标谓词）、路由骨架、上下文预算 | 源完成谓词（不再触发则**剪枝而非重调**）、数据特定后处理（SMILES）、评估器特定假设 |
| 换模型 | 终端/进程层、拦截计数、prompt 注入管线、交付物观察层 | 检索预算按模型容量重调、干预时刻（时间/步数阈值） | 生命周期控制（重校准拦截启发式）、rubric 分类（重写反例） | **针对单一模型输出的 parser 修补**、输出 schema/解码契约、干预强度、环境特定 bypass |

总结论（§F.5.4 末）：**benchmark 变 → 完成所需证据变；model 变 → 处理 policy 失败的方式变**。稳定接口favor复用；输出修补与干预阈值必须对目标场景重验。

量化佐证：Opus 与 Gemini 各自演化的 harness 终端/进程结构几乎相同且迁移后保留；parser 修补（未转义控制符、非法转义、截断响应）是模型特定的。零分率 Opus 0.09% vs Gemini 4.49% → 干预阈值不能跨模型照搬。

## 3. 可移植的 harness 机制清单（论文案例里的具体工程件）

以下都是论文里被演化出来、且被证明可迁移的机制，UH! 内核/能力层可对照取材：

### 3.1 执行证据完成门（ExecutionGatingInterlock，§F.2）★ 最有价值

- 跨轮状态机，在 agent 声明完成时拦截。源端 4 条拒绝路径：
  - Case 0：完成请求时刻检测到终端错误（崩溃/断言失败/HTTP 404/测试错误）；
  - A：上一轮有错误且本轮无命令实际执行；
  - B：上一轮输出被截断丢弃命令块且本轮无执行；
  - C：整个会话累计执行 ≤1 条命令就要完成。
- **连续拒绝上限 3 次**，到顶放行——"never lock out a done task"（防死锁是硬约束）。
- 二次确认（pending）直接放行，不重复拦截。
- 目标端扩展：检测"约束检查通过 + 打印 score/cost"的输出签名 → 提示**可行 ≠ 最优**，要求对照理论界量化次优差距；最终形态 = 阻塞"自报不可行"（如 `"route_feasible": false`）+ 警告"可能次优"。
- 演化轨迹：137 行（r6）→ 275 行（源结束）→ 437 行（目标结束）。无 SIM 的对照运行对同一个门改了 4 次、2 次在修自己造成的完成死锁，还把继承的门误认为自己第一轮的产物。

### 3.2 交付物注册检查（workspace，§F.5.3）

- 失败模式：文件写到了磁盘但没经 `write_file` 注册，评估器不认。
- 检查依据从**文件系统探针**换成**工具调用历史**（目标端失败来源变了）。
- 三级单发干预：检测到存文件 → 提示；步数预算过 75% 仍未注册 → 强制指令；`final_answer` 时 → 条件阻塞。
- 注意其前提假设：评估器按注册记账。换评估器（直接读输出目录）则整条机制作废——**机制要连同其成立假设一起记录**（这正是 SIM provenance 的用途）。

### 3.3 中间产物检查点（engineering，§F.5.4）

- 把**超过基线分**的中间产物写盘保护，防无预警超时清零。源端一次性检查 → 目标端持续检查点协议。

### 3.4 其他

- 长输出 head-and-tail 截断，配额放大 3×/5×（workspace）。
- 步数预算提醒：两个 coding 分支都在目标第一轮独立加了"剩余步数触发提醒"（源端不需要）；Opus 用墙钟（每 600s，至多 3 次），Gemini 用步数比例（0.8 / 0.75）——**触发变量本身是模型依赖的**。
- 长命令走 paste buffer 传输 + 超时后保留 stdout/stderr + 后台进程退出码检查（coding 工具层，跨模型稳定复用）。
- 拒绝处理（safety refusal 检测）继承后在目标闲置——**闲置 ≠ 无益也无损**，保留但不计入迁移收益。

## 4. UH! 落地建议（三层，按侵入性排序）

### 层 A：工程流程立即能用 —— 把 DSH/Codex 协作循环 SIM 化（不动契约）

UH! 现有的"brief → 派发 → 审 diff + 门禁 → 落提交"循环**就是**一个 harness 优化循环：Codex ≈ proposer，DSH ≈ selector，pytest + verify-all ≈ evaluator，briefs/ + docs/reviews/ ≈ 散落的记忆。论文的核心发现直接适用：**只留最终代码（harness）不留"为什么改、预期修什么、实测如何"，换模型/换阶段续做时会重复试错、误改继承组件**——M1 五轮审查里"修了又坏、坏了又修"的往返正是这个形态。

做法（新增文件，不改冻结物）：

1. 建 `docs/reviews/improvement-memory.json`，采用 §1.1 schema，映射：
   - `domain` → `{milestone, issue, 实现模型, 审查模型}`（如 `m1/codex-gpt6`）；
   - `predicted` → brief 里**预先写明**预期修复的 issue/测试名（评估前锁定）；
   - `fixed/missed` → 门禁与审查实测回填；`passed/total` → pytest 通过/总数；
   - `what` → 修改 + 理由（对应 brief 的"目标/需求"）；`files` → diff 涉及文件。
2. brief 模板增补一节 `## 预期修复（predicted）`；审查报告收尾时回填 fixed/missed，**被接受但没修好的照样入账**（P8 教训：accepted ≠ fixed）。
3. 根因条目跨里程碑继承：后续新 brief 的"必读上下文"注入 improvement-memory 相关条目（全文注入，条目少时可行；多了再摘要+expand，参考 DSH memory-evolve 的渐进披露）。
4. 换实现模型时（Codex→其他，或模型升级）执行 §1.3 规则 2/4/8：核对每条经验的来源模型，**复用理由、重估实现**，任务级证据降权。
5. 可用真实历史冷启动（标 `backfilled: true`）：M1 二批修复的 bus→task 桥、StorageGuard 接线、step.failed 配对都是现成的根因条目。

收益预期（类比论文）：减少审查往返中的重复试错与"误改继承组件"；换模型续做时保住源阶段经验。成本：每轮 brief/审查各多写一小节。

### 层 B：内核设计输入（M2+，走新契约编号 + 评审，只增不改）

1. **完成证据门**（对应 task-flow 终态语义）：task-flow 决议 F4 只规定终态"三选一、必居其一、必送达"（task.finished / task.failed / task.cancelled），**未规定 finished 的证据要求**——目前由执行侧声明即终态。论文证明"完成是需要证据的特权"。建议新契约提案（只增，不动 F4）：task.finished 发射前过证据门（执行发生、无未处理错误、交付物已注册），**拒绝次数有上限、到顶放行**（防死锁），门的事件进事件字典（新增编号，18 事件只增不改）。这是 §3.1/3.2 的直接移植，且与 M1-8 高危确认机制正交（确认管"能不能做"，证据门管"做没做完"）。
2. **改进记忆 ≠ 任务记忆**：M1-5 长期记忆是语义召回 + L2/L3 隐私分级的任务/用户记忆；SIM 是**优化器经验**（工程数据，无隐私分级需求，结构化按根因聚合，小体量全文注入）。建议作为记忆层新模块而非塞进现有召回管线——两者读写模式完全不同（SIM 无检索、按根因 append-only）。
3. **多模型校准层分离**（对应 UH! 多模型可插拔卖点）：按 Table 8 把 harness 切成"稳定接口层"（工具执行、事件总线、拦截点、交付物观察）与"模型校准层"（parser 修补、干预阈值、输出 schema、预算触发变量）。换模型时只重验校准层。论文实证：不分离时继承 harness 在新模型上**起点低于种子**（−0.60 ~ −5.48），盲目继承是负收益。
4. **评估器假设入账**：任何依赖评估侧行为的机制（如注册记账）必须把假设写进记忆的 provenance；换评估器时先重估假设再谈复用。

### 层 C：风险与边界（照抄论文会踩的坑）

- **token 预算**：论文全文注入成立的前提是 ~10 条目、每条 what 截断存储。UH! 工程记忆会长到几十上百条，需要"摘要注入 + 按需 expand"（DSH memory-evolve 已有此模式），否则重演上下文膨胀。
- **accepted ≠ fixed**：只记成功修复会系统性高估经验质量；P8 两次被选中 0/4 兑现仍入账是刻意设计。
- **自改讨好评估器**（论文 Ethics 承认）：自改 harness 可能满足 verifier 而不解决任务。UH! 对应物 = 门禁与验收分离（门禁绿 ≠ 验收过），held-out 思路 = 审查用独立模型/独立环境（M1 三模型审查已在做，保持）。
- **单运行证据**：除 coding 配对外都是单次运行描述性结果；层 B 的提案立项时应自带重复验证计划，别把论文幅度当承诺。
- **仅根因不够**：Problem-Only 消融不稳定（−1.82 ~ +2.40）——如果只做"问题清单"不记修改/预期/实测/来源，大概率白做。这是层 A schema 不能偷工减料的依据。
